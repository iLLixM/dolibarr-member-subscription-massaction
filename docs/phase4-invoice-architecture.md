## 2. Reconstructed business contract

### 2.1 Invoice requirements

The following records combine original behavior/source, existing preparation, missing behavior, API dependency, conflict and architecture consequence. Planned evidence is detailed in the implementation plan; no invoice test is currently claimed as passed.

**C05-01 — Optional invoice.** H `Adherent::createSubscriptionWithOptions()` at line 2398 accepts invoice independently from confirmation mail. M has invoice-aware preview internals, but forms, confirmation and booking reject invoice/autocreate. Preserve subscription-only booking without invoice/third-party dependencies or extra rights. Add a confirmed invoice boolean only after the write path is qualified. Missing: all invoice writes and their real tests. O1 now supersedes both the original invoice-on default and Phase 3B's disabled default with an entity-configuration-dependent initial selection; the original C08-03 text is preserved.

**C05-02 — Core invoice flow.** H calls `subscriptionComplementaryActions(..., 'invoiceonly', ...)`; C04-02 requires business APIs rather than copied INSERT logic. No invoice adapter exists in M. Proposal: use `Facture::create/addline/validate` directly through a small adapter, retaining equivalent defaults and triggers. The wrapper also reads request links and generates PDF before the owner's commit, with no PDF-result propagation. Reusing that entire wrapper conflicts with the desired boundary; equivalent orchestration of its business APIs is justified, not abandoning Core integration.

**C05-03 — Existing linked third party.** H `subscriptionThirdPartyForBatch()` line 2271; M same-named method already checks fetch, sharing and object access. A broken/inaccessible existing link is a row error, never permission to create a replacement. No invoice: no obligation to create a third party. Missing: transactional re-fetch/locking and confirmation of relevant customer fields. Use `Societe::fetch`, `getEntity('societe')` and object access; verify invoice/customer/member entity relationship explicitly. Shared-entity behavior still needs real qualification.

**C05-04 — Explicit optional creation.** Same H source. M only plans creation when invoice+autocreate are true, third-party creation is allowed and member entity equals current entity. Missing: actual `Societe::create_from_member`, persisted link verification and rollback tests. Its nested transaction copies member identity/address/contact data and may create a contact; it does not promise deduplication by name/email. Lock/reload member, recheck it still has no link and validate customer-code/contact configuration. Reload member after creation. Never infer consent from POST, missing access, or an existing customer with a similar name. O3 approves this design with the supported-profile restrictions below; actual side effects still require qualification.

**C05-05 — Individual gross amount.** H combined booking and amount helper at line 2079. M resolves each nonnegative finite type amount, falling back only for null/empty to latest contribution by `datec DESC,rowid DESC`; zero stays zero. Missing: real invoice totals. Core line input uses quantity 1, price base `TTC`, gross amount in `pu_ttc`; Core computes HT/VAT/local taxes/totals. Revalidate amount/type under lock and verify stored totals at configured monetary precision, not floating-point exact equality. Packaging/currency/tax configuration can alter totals: reject unsupported combinations explicitly rather than changing the confirmed fee.

**C05-06 — Description, product/service and VAT.** H description helper `htdocs/adherents/lib/subscription_options.lib.php:110`, plus combined booking. M `msmDescription` and product/stock preflight are preparation, not invoice evidence. Three literal tokens (`{Member type}`, `{Start date}`, `{End date}`), valid UTF-8, at most 1024 template characters, no control/format characters; unknown tokens remain literal. Use the resolved individual description; retain original template in fingerprint. Core invoice description is HTML-capable: encode plain text once at that adapter boundary and test actual PDF/HTML output, not blindly reuse escaped UI output. H escapes label before both destinations; M currently stores subscription description as plain text. Preserve M's subscription behavior and avoid double escapes. Core configured product and VAT rules are examined in section 5; O4 resolves policy, not an invented customer-tax rule.

**C05-07 — Link actual contribution and invoice.** H sets `linked_objects['subscription']` to the newly returned contribution ID before invoice creation. No implementation in M. `Facture::create` invokes `CommonObject::add_object_linked`; persist source type `subscription`, target type `facture`, with correct IDs. This is inside the same database transaction. Check exact relation after creation; absent/wrong/extra unexpected relations fail the combined row. Neither membership ID nor type ID is a subscription ID. Existing invoices/contributions are not retroactively invoiced, reused, canceled or repaired by this feature. Core views are expected to expose standard linked objects; exact navigation must be browser-qualified.

**C05-08 — Immediate validation.** H validates after adding the line, before outer commit. M invoice rights preflight is only preparation. Core validation changes draft to validated, assigns final reference and may invoke stock/trigger/filesystem behavior. Recheck invoice creation/read and advanced validation rights; invoice-send rights apply when selected. No silent draft-only fallback. Failure rolls back the whole member transaction when its outcome is known. Keep payment/bank operations excluded. PDF generation is not directly inside `validate()` in the inspected versions; section 6 distinguishes remaining side effects.

**C05-09 — Core PDF.** H delegates generation to the complementary-actions wrapper; M has no generation. The wrapper's placement before outer commit and ignored return do not satisfy a reliable post-commit PDF status. Proposal: generate explicitly after confirmed commit, using validated invoice identity/model/language and then verify the actual canonical PDF. Failure is a document warning with retained invoice/contribution; not a failed database booking. Core document generation also writes metadata; it is not a pure filesystem operation. O2 approves the architecture boundary only; residual pre-commit effects still require separate risk acceptance after integration evidence.

**C05-10 — Zero fee.** H amount helper explicitly permits zero; M preview and subscription scope retain it. A selected invoice is still required for a zero fee, not silently omitted. `Facture::validate` requires a line, not a strictly positive total in the inspected standard path. Core numbering/models/tax/custom triggers still need a real zero-invoice test. No payment record or automatic settlement is implied. This is required behavior, not a new owner choice to reject zero.

**C05-11 — Combined rollback versus post-commit warnings.** H outer transaction aims to include contribution and invoice; the historic catch drains transaction counters. M now has conservative ownership/depth checks and R16 verification. Extend those checks; do not port the old drain loop. Creation/link/line/validation/integrity failures before commit roll back contribution, new third party/member link and invoice together when rollback is verified. PDF/SMTP failures after commit retain both. Unknown commit/rollback means unknown outcome and batch stop, never success, retry or compensating deletion. Real invoice rollback evidence is missing.

**C06-05 — Safe invoice PDF attachment.** H `sendSubscriptionConfirmation()` line 575 requires the invoiced contribution's canonical readable PDF within the invoice entity root, rejecting path escape. M standard subscription mail intentionally has no attachments. Missing: verified invoice attachment capability, hook boundary and real evidence. Do not attach the newest file, arbitrary template attachment, a request path or a different invoice PDF. O5 resolves the earlier “optional PDF” ambiguity: mail remains optional, but invoice+mail requires the verified invoice PDF for standard delivery, with no separate attachment checkbox. Missing PDF blocks standard send and becomes a post-commit warning, not a rollback.

## 5. Customer, monetary and object integrity

**Customer creation:** physical person uses member full name; legal entity uses company name with member-name alias; address, postal code, town, country, phone, email and social fields are copied by Core. Customer-code generation and `THIRDPARTY_CUSTOMERCODE_EQUALS_MEMBERREF`, optional default contact creation and mandatory fields need preflight. Existing customer is reused only by existing verified member link. No automatic email/name matching, linking an arbitrary supplied ID, or creation for a foreign-entity member. If another cooperating request creates the link first, fresh snapshot differs: skip/reconfirm instead of using stale creation consent. Existing customer promotion by invoice validation must be disclosed (O3).

**Price/VAT:** `ADHERENT_PRODUCT_ID_FOR_SUBSCRIPTIONS` supplies an optional accessible sale-enabled product/service. No product means a service line. Core `get_default_tva($mysoc, $mysoc, productID)` is used by the membership wrapper when `ADHERENT_VAT_FOR_SUBSCRIPTIONS == 'defaultforfoundationcountry'`; otherwise its VAT starts at zero. This is not the same as generic customer-country VAT selection. Core line calculation handles net/gross and local-tax machinery; passing zero local-tax rates is the historical mapping. O4 selects existing single-contribution membership parity, not a new customer-tax policy. Do not invent tax policy or a separate tax engine.

Core packaging can change quantity even if caller requests 1. Preserve stock-on-invoice blocker; preflight supported product configurations and reject a changed quantity or rounded gross total before commit. Inspect rounding globals, company currency, customer currency/exchange context, tax source codes, exemptions and mandatory fields. Proposal is company-currency standard invoices first; mixed currencies/local-tax regimes require explicit qualification before claiming support, not silently mispricing them. Zero remains valid. Credit notes, discounts, deposits, situation invoices, payment and accounting posting workflows are not new module features.

**Description:** keep resolved plain text in confirmed state and subscription input. Invoice HTML-capable description gets one explicit plain-text-to-safe-HTML conversion. Test `&`, `<`, quotes, non-ASCII and literal unknown tokens through Core rendering/PDF/mail. Keep original template and resolved result in snapshot; same rendered text from changed template still invalidates confirmation. Avoid trusting a pre-escaped preview field.

**Link:** set only `linked_objects['subscription']=newID` before `Facture::create`. Do not import `other_linked_objects` from requests (the wrapper does). Read back one expected source/target relation and correct member/customer/invoice ownership; duplicate/unexpected relation is an integrity failure, not an instruction to create again. Core `fetchObjectLinked` and invoice linked-elements UI are the integration path. Qualify the contribution-side navigation separately; do not promise a new backlink widget without implementation.

## 6. Transaction and failure model

**Recommended sequence, per member:**

1. Authenticated confirmation freezes invoice/autocreate/mail selections, resolved values, rights-relevant context and overlap consent; consume and persist it before business effects.
2. Reject foreign/open transaction; verify mysqli, InnoDB and supported Core/configuration profile. Begin one owned transaction.
3. Lock member, then type and relevant existing customer/product rows in a consistent documented order; reload current contribution history, user rights, entities and configuration. Compare extended fingerprint and overlap snapshot. Locks do not make configuration/external systems immutable.
4. Call existing guarded subscription API with no payment/account inputs. Verify persisted fee/dates/type/member and R16 end-date result.
5. Reuse verified customer or explicitly create it through Core; re-fetch and verify member link. Create standard invoice with subscription link, add single gross-priced line, validate. At each boundary require normal return and expected transaction depth/server state.
6. Verify contribution/R16 again after invoice triggers, invoice customer/entity/status/final reference, one expected line, gross amount/currency/product/description and link. Verify newly created customer linkage too. Reject unsupported changes rather than quietly accepting trigger-rewritten business values.
7. Commit once from owner depth 1; require successful return and inactive physical transaction/counter zero. Save combined IDs and committed status before post-commit effects.
8. Re-fetch and authorize invoice; generate/verify PDF; save document status. If mail selected and prerequisites pass, use post-commit mail and checkpoint outcome. Finish with separate DB/PDF/mail statuses.

Subscription-first matches history, obtains the exact link ID and avoids customer creation before the subscription check succeeds. Customer-first inside the same transaction is viable but gains little and fires customer hooks earlier. All operations use the same DB connection; a hook opening another connection or committing directly breaks this model.

**Atomicity qualification:** an outer InnoDB transaction can cover these normal nested Core database writes. It cannot roll back emails, remote calls, file writes/renames, nontransactional trigger tables, or committed work on another connection. `Facture::validate` renames existing PROV files/directories; the new invoice normally has no generated draft PDF, but that is an inference, not a guarantee about hooks. Never claim “no filesystem effects before COMMIT”. No global PDF-disable toggle, trigger suppression or source patch is proposed. Review actual enabled triggers and document models before allowing invoice writes; unsupported or insufficiently controlled side effects block that environment pending technical qualification and separate invoice-risk acceptance; O2 itself is already decided.

Extend the engine/table check beyond Phase 3B's three tables: invoice/header/details/extrafields, `element_element`, customer/contact/link tables when used, numbering persistence, agenda/audit and any configured trigger tables. Determine the exact touched set from the installed profile; do not claim a universal fixed list or attempt auto-migration. Keep normal Core triggers enabled. Workflow, Agenda and BlockedLog are concrete reasons not to assume invoice creation touches only two tables. Custom numbering can be externally stateful. A successful Core return is not proof of isolated side effects.

| Boundary | Database result | PDF/mail and batch behavior |
| --- | --- | --- |
| Invalid rights/configuration/stale confirmation before writes | Skipped, no new business object | No PDF/mail; eligible later rows may continue. |
| Contribution/customer/create/line/link/validate/postcondition fails; owned rollback proven | Failed; all row's transactional changes rolled back | No PDF/mail; continue only with known clean connection. Log safe stage, not SQL/private errors. |
| Unexpected nesting, lost connection, uncertain commit or rollback | Unknown; IDs if known are evidence, not confirmed success | Stop entire batch; no PDF/mail/retry or compensating delete. Manual authorized reconciliation. |
| Confirmed DB commit; PDF fails/missing/unreadable/unsafe | Contribution and validated invoice remain successful | Document warning; required standard invoice mail not sent. Continue other rows. |
| Confirmed commit and PDF; SMTP/hook failure | Objects and PDF remain | Distinct failed/handled/unknown mail result; no automatic resend. |
| Session checkpoint fails after commit | DB may already be committed | Stop processing; no rebooking. Available Core links aid reconciliation but do not reconstruct lost consent. |

Do not copy H's `while(transaction_opened) rollback()` cleanup. A leaked nesting level after an exception must produce uncertainty and stop, not decrement counters until a “clean” appearance. Closing an owned connection may cause server rollback of uncommitted work, but is not evidence of a previously acknowledged/unknown commit. This must be tested with controlled adapters and then separately authorized real connection tests.

## 7. PDF, mail, permissions and replay

PDF is an explicit post-commit operation even when no email is requested (C05-09). `generateDocument` uses Core's configured model/language; capture negative returns, warnings and exceptions. It can update ECM/`last_main_doc` after writing the file; verify path and distinguish readable document from metadata failure. Do not delete an existing artifact to “roll back” a validated invoice. No generation, repair, resend or booking on result GET. Later manual regeneration uses the authorized Core invoice UI; automatic recovery would need its own authorization/design.

Resolve the canonical `<entity invoice root>/<sanitized final ref>/<sanitized final ref>.pdf` from persisted invoice identity, not browser/session path. Require configured entity-specific root, validated invoice access, readable regular PDF, canonical parent/root relationship and no escaping symlink. Do not fall back to another entity's root or newest file. Recheck immediately before transport and consider file replacement races; a path check alone is not a filesystem immutability guarantee. No arbitrary attachment arrays from POST. Templates generating other formats need explicit qualification; mere `generateDocument > 0` is insufficient.

Keep `MsmSubscriptionMail`'s independent mail-off fast path, fresh rights, language/templates/type text and finally restoration. For invoice mail pass immutable verified invoice identity plus artifact descriptor. A positive `sendMail` hook owns delivery/suppression; show **handled**, not **sent**, and do not claim its attachment was the standard PDF. A zero hook outcome permits standard delivery only after revalidating replaced object/action/entity/recipient and invoice relationship; negative/exception yields warning. Required invoice PDF validation must occur before invoking a hook intended to receive that attachment context. Arbitrary third-party hooks remain a trust boundary and require inventory/qualification; standard code cannot guarantee their transport policy.

Invoice mode requires internal member read/subscription creation, invoice module/read/create, third-party read/access; advanced invoice validate and send permissions when applicable. Autocreate additionally requires third-party creation and current entity. Re-evaluate before each row and post-commit delivery; a lost right after commit suppresses delivery without undoing business records. Product access, customer sharing, document root and endpoint entity checks are independent. Do not rely solely on global invoice rights or on the unscoped link table.

Extend confirmed snapshot with existing customer identity and invoice-relevant address/tax/payment fields, product type/status/tax/packaging, invoice currency/date policy, relevant tax/rounding/numbering/model configuration and explicit option values. For planned customer creation include the copied member fields and contact/code configuration. Freshly derive and compare; include values, not just IDs. A fingerprint is a change detector, not authorization or a lock. Document unavoidable races with non-cooperating configuration/rights updates.

Introduce a new state format that invalidates old confirmations and returns them to preview with fresh explicit choices. Never reinterpret a consumed/done run as editable. Keep owner/entity/expiry/revision and POST allowlists; do not accept invoice/customer IDs or amounts as booking commands. Proposed result additions: contribution ID, invoice ID/ref, customer ID/created flag, DB outcome, PDF outcome, mail outcome, safe stage/message. Store scalars, not live Core objects, absolute private paths or raw exceptions. Invoice links require fresh access checks.

O6 retains session checkpoints for the first controlled implementation, with explicit manual reconciliation and **no exactly-once/recovery promise**. No new module table, durable journal, automatic resume, rebooking, reinvoicing or resend is included. A journal remains a later production decision; it would add schema, retention/privacy/migration and deployment obligations and still could not make SMTP exactly-once. Existing contributions/invoices are never reused merely because a lost run looks similar. Core links are evidence, not an idempotency key.

### 7.1 Manual Reconciliation of Unknown Invoice Booking Outcomes

Purpose: determine what is known after a stopped/unknown run without creating, repairing, deleting, validating, regenerating or resending anything. Do not automatically resume the batch. Use an authorized read-only account and a consistent observation of the authoritative database; an absent row on a replica/stale snapshot or while a transaction is still unresolved does not prove failure.

1. Identify run/member, owner/entity, code versions, time window, last completed stage and confirmed start/end, fee, type, description and invoice/autocreate/mail choices. Use surviving server state and sanitized retained evidence. If original parameters are unavailable, record that uncertainty; never reconstruct consent from a matching current record alone.
2. Read candidate contributions for that member and timeframe; compare IDs, type, dates, fee, author and description against the confirmed snapshot and before-state. Include other writers' possible records; identical values alone are not attribution.
3. Read candidate invoices using recorded IDs first, then authorized customer/entity/date/amount searches. Verify actual stored fields/lines, not only a UI count or preliminary ID returned before commit.
4. Read `element_element` source `subscription` → target `facture`. Verify exact new contribution/invoice IDs and both endpoint entities/rights. Missing, multiple or inconsistent links leave the combined operation unconfirmed.
5. Verify member→customer link, customer identity/classification and any possible newly created customer/contact. Compare before-state to distinguish reuse, promotion, creation or an unrelated change. A newly allocated ID alone does not prove commit.
6. Check invoice status and final reference/numbering context. A draft, provisional reference or unexpected final number is not the required validated success; a number gap is not proof of an invoice or a failed transaction.
7. Recheck contribution fields and stored member end against the Core/Phase-3B R16 rule (latest contribution by start date, not simply maximum end). Use recorded end-update outcome where available; a later correction cannot retroactively prove the original transaction succeeded consistently.
8. Read canonical invoice PDF and document metadata if separately authorized. Check invoice/entity/ref association, readability, generation evidence and metadata consistency. Existing PDF does not prove DB commit, and missing PDF does not refute a confirmed DB booking. Do not regenerate during reconciliation. Mail/hook evidence is separate; missing delivery proof is not permission to resend.
9. Classify using the evidence table below, including any conflicting observations. Distinguish successful combined DB booking from unresolved PDF/mail, and row-local certainty from batch-wide uncertainty.
10. Save a sanitized report with run/member/object IDs, observation time/source, compared values, known/unknown stages, evidence references, classification, reviewer and proposed manual follow-up. Any corrective Core operation, new booking, document generation or mail requires a separately reviewed explicit authorization; never automatic compensation or retry.

| Classification | Required evidence | Allowed conclusion |
| --- | --- | --- |
| Definitely not executed | Reliable pre-write rejection/stop evidence tied to this run plus consistent read-only corroboration | No operation by this attempt; still no automatic new booking |
| Confirmed successful | Persisted matching contribution, validated invoice/final reference, correct link/customer/entity and R16, with sufficient run attribution | Combined DB success; PDF/mail evaluated separately |
| Known proven rollback | Positive owned rollback evidence/clean transaction outcome and before/after readback for all affected transactional objects | This row's transactional writes rolled back; external effects still separate |
| Unknown/unresolved | Missing original parameters, ambiguous commit, conflicting records, incomplete links, unresolved live transaction or insufficient attribution | Keep stopped; record exact uncertainty and escalate for manual review |

The later implementation should make available bounded sanitized evidence: run ID, owner/entity/member, confirmed value/config fingerprint and relevant comparison fields, stage timestamps, before-state identifiers, returned contribution/customer/invoice IDs, transaction-depth/server-state and commit/rollback results, persisted postconditions/R16, PDF identity/status and standard/hook/mail outcome. No credentials, tokens, full private records or raw SQL exceptions. Use the approved protected persistent test-results location for authorized test evidence and normal session checkpoints; this is not a new module journal/table or a guarantee of production crash recovery. Missing evidence remains missing. Define concrete file names, retention, access and read-only queries during 4C, and review this procedure against actual implementation **before authorizing real 4C integration tests**. No reconciliation script or schema is created here.

### O1 — Decided: configuration-dependent initial invoice selection

For a **new** run, read `getDolGlobalString('ADHERENT_BANK_USE')` from the authenticated application's current entity configuration. The design rule is the strict comparison `ADHERENT_BANK_USE === 'invoiceonly'` (using the getter's string value), not a truthy/nonzero test.

| Effective value | Initial invoice selection, when the option is available |
| --- | --- |
| `invoiceonly` | Checked |
| `bankdirect` | Unchecked |
| `bankviainvoice` | Unchecked |
| `0` | Unchecked |
| Empty, missing, unknown or any other value | Unchecked |

Four distinct gates apply: (1) configuration suggests the initial choice, (2) required invoice/third-party modules and supported profile make the option available, (3) fresh user/object/entity rights permit it, and (4) the complete implemented and qualified write path permits execution after explicit final confirmation. A suggested check never grants permission. If unavailable, show the reason and no executable invoice selection. When available, the user may check or uncheck regardless of the default. Autocreate remains unchecked; mail retains its independent configured default. Phase 4B may prepare/read these choices but must still reject invoice writes.

Evaluate the default only at creation of a genuinely new preview/run. Store the user's effective selection server-side; refresh, edit and confirmation revisions must not overwrite it. Include the effective `ADHERENT_BANK_USE` string and entity in the relevant configuration snapshot/fingerprint. A later change makes the previous confirmation stale: require fresh review/reconfirmation, preserving the existing user choice rather than silently reapplying the default. Entity changes invalidate the owner/entity-bound run. Old session formats must not inherit invoice consent: require explicit fresh selection/reconfirmation on migration, never reinterpret consumed/done runs as new.

**Targeted Core evidence:** both versions save the setting with `$conf->entity` and read it using `getDolGlobalString`. The getter returns the string from the already-loaded `$conf->global`; it does not select an entity itself. Use normal authenticated bootstrap/current entity, not a hardcoded entity or direct global SQL lookup.
